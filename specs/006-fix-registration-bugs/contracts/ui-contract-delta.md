# UI Contract Delta: Registration Portal Bug Fixes

This feature does not add or remove any route from `004-event-registration-portal/contracts/ui-contract.md`.
It fixes behavior inside four existing surfaces. Only what changes is documented here — everything
else in `004`'s UI contract (routes table, component list, Server Action shapes, error-surfacing
table) stands as-is.

## `/events/[eventId]` — not-found handling (defects #3, #6)

| | Before | After |
|---|---|---|
| Not-found rendering | Inline branch in `page.tsx`, wrapper `<div className="mx-auto mt-12 max-w-md p-4 text-center lg:p-6">` — renders at a fraction of its intended width inside the flex-column `<main>` (missing `w-full`) | `page.tsx` calls `notFound()` for `NOT_FOUND`/`VALIDATION_ERROR`; a new sibling `not-found.tsx` renders the card with `<div className="mx-auto mt-12 w-full max-w-md p-4 text-center lg:p-6">` — full available width up to `max-w-md`, matching the success-path wrapper's pattern. Any other error code (unexpected 5xx/network failure) keeps an inline fallback card instead, now with the same `w-full` fix, rather than being misreported as "not found." |
| HTTP status for an unresolvable `eventId` (real 404 from `apps/api`, or a 400 `VALIDATION_ERROR` from a malformed/non-UUID `eventId`) | `200`, normal successful page, no `noindex` | Still `200` at the wire level — this route's (and its parent `/events` list route's) `loading.tsx` causes Next to stream the response before `notFound()` runs, so the status can't change after the fact (documented Next.js App Router behavior, not specific to this fix). What *does* change: Next's own `<meta name="robots" content="noindex">` tag is now present (confirmed live), the dedicated `not-found.tsx` boundary renders, and Next's internal routing state correctly treats the page as not-found — the standard "soft 404" pattern. A literal `404` status would require a `proxy` (middleware) pre-check duplicating this page's own fetch on every request; out of scope for this fix (research.md #3). |
| `RegistrationPanel`'s `useSyncExternalStore` third argument (`getServerSnapshot`) | `() => getMyRegistrationForEvent(event.id)` — reads live storage during hydration too, causing a one-time hydration-mismatch console exception whenever the visitor is already registered | `() => undefined` — a fixed placeholder matching what real SSR always renders; no console error, `getSnapshot` still picks up the real state immediately after hydration |

`AlreadyRegisteredCard` / `RegisterForm` / "registration closed" branches are otherwise unchanged —
only *which* function computes the value they branch on, and *when* it's evaluated, changes.

## `/my-registrations` — live-event fetch result (defects #2, #6)

`fetchEvent`'s return type changes from `Promise<EventResponse | null>` to the tri-state
`LiveEventState` union defined in `data-model.md` (`'loading' | 'ok' | 'not-found' | 'unreachable'`).
Concretely:

| Fetch outcome | Before | After |
|---|---|---|
| `GET {NEXT_PUBLIC_API_BASE_URL}/events/:eventId` → `200` | `EventResponse` | `{ status: 'ok', event }` |
| → `404` | `null` | `{ status: 'not-found' }` |
| → any other non-2xx status | `null` | `{ status: 'unreachable' }` |
| `fetch()` throws (network error, and — before the CORS fix — every request, since none could reach page JS) | `null` | `{ status: 'unreachable' }` |
| Not yet resolved | `undefined` (React state default) | `{ status: 'loading' }` |

`MyRegistrationListItem`'s `isDeleted` prop derivation changes from `liveEvent === null` to
`liveEvent?.status === 'not-found'`. `'unreachable'` renders identically to `'loading'` today (falls
back to `record.eventSnapshot`, no "no longer available" badge, no crash) — this is the FR-005 fix:
"unreachable" is no longer visually or logically equivalent to "deleted."

`MyRegistrationsList`'s `useSyncExternalStore` third argument (`getServerSnapshot`) changes from
`getMyRegistrations` (reads live storage) to `() => []` (a stable empty-array placeholder) — same
hydration-safety fix as `RegistrationPanel`, applied to the list-level store read.

## `apps/web/src/app/layout.tsx` — portal metadata (defect #4)

| | Before | After |
|---|---|---|
| `metadata.title` | `"Create Next App"` | `"Event Registration Portal"` (exact copy is an implementation choice; must identify the product, not `create-next-app`'s scaffold string, per FR-008) |
| `metadata.description` | `"Generated by create next app"` | A short, accurate one-line description of the portal |

No `generateMetadata` is added to any route segment — every route continues to inherit this single
root value (spec Assumptions: one portal-wide title is sufficient).

## `packages/shared`'s `EventFormDialog` consumer — Image URL message (defect #5)

No component-level contract change — `EventFormDialog` (`components/admin/event-form-dialog.tsx`)
already renders whatever message `buildEventFormSchema`'s Zod resolver attaches to `errors.imageUrl`
via `FieldError`. Only the message text changes when the field is left empty (`"Image URL is
required."` instead of `"Enter a valid image URL."`) — see `data-model.md`. No prop, event handler, or
DOM structure changes in `event-form-dialog.tsx` itself.

## Error surfacing table (`004`'s contract) — no changes

The existing HTTP-status-to-UI-treatment table in `004-event-registration-portal/contracts/ui-contract.md`
is unaffected: `409 CONFLICT` on register still surfaces its message verbatim, `404` on cancel still
syncs local state, etc. This feature does not add or remove any error case at the Server Action layer
— defect #1's fix moves the "cancel-then-re-register" case from incorrectly hitting the `409` path to
correctly hitting the existing `201` success path, which already has a defined UI treatment
(`addMyRegistration` + confirmation).
